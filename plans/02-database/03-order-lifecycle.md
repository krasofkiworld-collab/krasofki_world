# Життєвий цикл замовлення

```
pending ──(адмін підтвердив)──▶ confirmed ──▶ shipped ──▶ completed
   │                                                          ▲
   └──────────────────(адмін/клієнт скасував)──▶ cancelled ───┘ (немає, cancelled — термінальний)
```

| Статус | Хто виставляє | Що відбувається |
|---|---|---|
| `pending` | система, при створенні замовлення | нотифікація клієнту "прийнято" + всім `staff_chats` "нове замовлення" |
| `confirmed` | адмін в `/admin/orders/[id]` | тригер списує `stock_quantity`; нотифікація клієнту "підтверджено, готуємо" |
| `shipped` | адмін (вписує ТТН у `admin_note`) | нотифікація клієнту "відправлено" + номер ТТН |
| `completed` | адмін | нотифікація клієнту "отримано, дякуємо" |
| `cancelled` | адмін (або клієнт через бота — post-MVP) | нотифікація клієнту "скасовано" + причина з `admin_note` |

`payment_status` змінюється незалежно від `status` (можна підтвердити замовлення до оплати — наприклад, оплата при отриманні). Значення: `unpaid → paid` (адмін тисне "Оплачено" вручну, або платіжний вебхук — див. `06-integrations/03-payments.md`), `paid → refunded` (ручне скасування з поверненням).

## Правило: не довіряти клієнту жодних цифр

`POST /api/orders` приймає лише `product_id`/`variant_id` + `quantity` з клієнта. Ціна, назва, наявність — завжди перечитуються з БД на сервері перед вставкою `order_items`. Якщо товару не вистачає на складі — `409` і Mini App показує помилку до створення замовлення.
